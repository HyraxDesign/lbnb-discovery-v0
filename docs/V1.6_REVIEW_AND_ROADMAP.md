# NAVA V1.6.1 — operational review and route to multi-user use

Baseline: HyraxDesign/lbnb-discovery-v0 main, bc9e7c1 (V1.5.1). V1.6.1 user review screenshots are the visual acceptance reference: restore listing media first, then show date-spread Journey days.
This batch is a local-persistence prototype. Accounts, real host requests and cross-device sharing are not enabled by this release.

## Product logic retained

Discover → Save → Journey → Plan → Request → Confirmed.
Saving dates creates a personal plan. Pending requires successful delivery to a connected host; confirmed requires that host's response. No confirmation reference is demanded from the traveller. Dates undecided remains available. No native payments or live inventory in the current scope.

- In-page range calendar for Journey and Stay dates, with check-in/check-out handling; native fields remain usable.
- Lebanon stays no longer attach to the Lisbon Journey. Stay anchors must match destination and overlap dated Journey bounds; declined/expired/cancelled stays do not become anchors.
- Vertical fullscreen reel navigation and keyboard arrows, with the carousel retained. Feed order stays stable during media hydration.
- Edit/save/remove plan wording and feedback; visible My and Journey views refresh after edits.
- Calendar displays all plans on a date instead of silently hiding all but the first.
- Malformed array storage no longer breaks Saved or Bookings.
- Media script is present directly in HTML, so a first visit does not require service-worker HTML injection.
- Recovered exact-match listing photos are served locally; listing image sheets expose recovered gallery items. The reel media renderer supports direct video URLs when present.

- Service worker caches only successful same-origin responses, handles query-string offline content lookup and updates to V1.6. Failed legacy image requests are not cached as usable media.

## Minimal backend design

One database and one API, not multiple services. Core records: users, places, units, media, journeys, journey_members, journey_stops, saves, plans, host_claims, plan_events and notifications. A plan has owner_id, journey_id (optional), place_id, unit_id (optional), date range, guest counts, state, revision and timestamps. The API owns transitions and host authorisation. Host claim approval precedes request routing. Store an event and notification in the same transaction as request/response; a retrying delivery worker handles optional email/push.

Keep personal → pending → confirmed/declined/cancelled/expired as the server model; convert the existing local planned label during migration. Never derive confirmation from a traveller-edited field. No old LBNB passwords are reused. The existing legacy source='host' field is prototype metadata and must not become an authorisation mechanism.
