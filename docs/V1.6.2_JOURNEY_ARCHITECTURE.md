# NAVA V1.6.2 — independent Journeys
AI proposes; the user creates. Suggestions, owned Journeys, Saved relationships and transactional bookings have separate identities.

## A — polish and architecture
- Explorer images are block-level covers, clipped to the existing 17px card corners. Progressive batches append 16 cards without replacing mounted cards. IntersectionObserver uses the Explorer scroll container; plain Show more remains the failure/unsupported fallback. No remaining count.
- Saved removal is a 35px button with a centred 14px SVG, outside the card's opening button.
- Use this journey always creates a new ID and deep-copied items. Dates belong to that Journey. Undated copies persist as drafts.
- Original V1.6.1 local keys are retained. Migration creates one owned Journey only if a legacy Journey was planned. Existing bookings preserve their identity and remain independent until deliberately attached. Replacements and order are migrated.

## B — real multi-day Journeys
- Owned Journey list, rename, duplicate, deletion, blank creation, and creation from selected Saved discoveries.
- One projection provides day modules to Timeline, Itinerary, Calendar and Map routes.
- Timeline trip overview and day zoom; edit action, pointer handles within/across days, keyboard reorder, and explicit day/time editor.
- First date selection distributes stop groups while retaining contextual Stories with their primary stop. Later edits persist; rendering never reallocates.
- Flexible/fixed modes. Booked dates are read from the booking, never changed by Journey arrangement.
- Inclusive Journey dates; maximum 366 days. Undated drafts retain their relative day allocation.
- Map currently provides per-day routes to Google Maps; embedded geographic basemap and live travel times remain future work.

## C — booking integration
- Separate bookingId and listingId permit repeat visits. journeyItemId is a reference, not a duplicate booking.
- Bookings can attach/detach to a matching destination; overlapping standalone dates offer attachment.
- Bookings created inside a Journey link immediately. Dates and status read from the same booking in both contexts.
- A Stay renders once as a span, with check-in/check-out nodes. Calendar nights exclude checkout; checkout remains a Timeline event.
- A domain transition reducer supports planned → pending → confirmed → cancelled. Host-event updates reproject the Journey. Confirmed bookings are fixed.
- **No host transport is connected in this static build.** User-created records are saved dates, never labelled pending or confirmed. Browser tests inject host events to validate the future adapter; they do not send real requests. A production authenticated server must supply and validate host events.

## D — intelligence foundation
- Personalised recommendation previews use Saved interests, destination, pace and booking context.
- Suggestions regenerate independently from owned Journeys. A selected-day preview can add selected recommendations without rearranging any existing or fixed item.
- Manual replacement offers alternatives. User approval applies changes to that owned Journey only.
- **The current recommender is deterministic context rules, not a connected AI model.** Generation, live opening times, geographic routing, availability and learned preferences need service integration. The original Stone, Sound & River is retained as a curated proposal.
- No AI credentials belong in static client files.

## Verification gates
1. Domain: independent copies and dates, source immutability, within/cross-day moves, fixed anchors, booking transitions, Stay night boundaries, DST, migration, and recommendation isolation.
2. DOM: Use this journey, Dates undecided, editing and view agreement, appended batches, SVG control, repeat bookings.
3. Mobile browser: Chromium and WebKit at 390×844, DPR 3; recovered image/gallery loading; image/frame geometry; SVG centring; automatic pagination; actual pointer drag across a day; zoom; all four views; booking projection and Stay span; reload and one-time migration.
4. Screenshots and JSON geometry reports are retained in the GitHub Actions artifact.
5. Release gate: successful checks before merging. Real iPhone PWA gesture feel and screenshots still deserve user review.

## Remaining milestones to multi-user
| Stage | Deliverable | Acceptance gate |
|---|---|---|
| Connected accounts | Authenticated users and shared persistence | A second user cannot read or modify the first user's private data; cross-device sync and conflict handling |
| Host operations | Verified host mapping, durable request delivery, host inbox and events | Real request received once; confirmed event updates the same Booking ID in every Journey view |
| AI service | Server-side generation with typed suggestion responses | Fixed anchors unchanged; source suggestion and user edits survive regeneration; opening hours and routes validated |
| Collaboration | Shared Journeys, invitation roles, notification preferences | Explicit access grants, revocation, event history and permission checks |
| Pilot | Travellers, hosts and administration | Full request lifecycle, cancellations, offline/reconnect, and mobile accessibility tested together |

## Release review corrections — 30 September 2026
- Guest counts use accessible 44px minus/plus buttons and non-editable outputs. Minimum adults, zero children, and unit capacity are enforced without a keyboard. Date and select controls use at least 16px text to avoid iPhone focus zoom.
- The Journey header reflects the current destination. Suggestion entry follows the latest Saved destination, or the visible discovery destination when Saved is empty. A context fingerprint refreshes recommendations when Saved or bookings change; destination selection and explicit refresh are available. Curated Stone, Sound & River remains inspectable separately.
- Suggestion previews have no date controls. Owned Journey dates remain local to that instance.
- Verification adds capacity and minimum boundaries, guest geometry, dynamic destination, refresh isolation, and absence of typing fields.
- Delivery must be verified separately from merge: the first V1.6.2 Pages run remained waiting at the github-pages environment gate while phones still displayed V1.6.1.
